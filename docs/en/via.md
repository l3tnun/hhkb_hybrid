# VIA support (editing the keymap in a GUI)

> English translation of [../via.md](../via.md). If the two differ, the Japanese version is authoritative.

When you flash QMK built with the `via` keymap, you can change the keymap, macros and keyboard-specific settings from [VIA](https://usevia.app) (a web app) without building. The changes are saved in the keyboard's built-in EEPROM and remain after unplugging and replugging, power OFF/ON, waking from sleep and flashing QMK again.

The behavior of the `default` keymap (no VIA support) does not change. Choose the `via` keymap only if you use VIA.

## Requirements

- Chrome or Edge (VIA uses WebHID, so Firefox / Safari do not work)
- A USB connection (settings in VIA are made over USB only. You cannot configure while connected over Bluetooth)
- On Linux, the keyboard's `hidraw` must be readable and writable by a regular user (udev rule. [setup.md](setup.md))

## 1. Build and flash

```sh
./tools/build.sh via
python3 tools/qmk_to_hfb.py qmk_firmware/.build/hhkb_hybrid_via.bin local/HHKB800_FW_A048.hfb local/hhkb_hybrid_via.hfb
python3 tools/flash.py --list
python3 tools/flash.py --device /dev/hidrawN local/hhkb_hybrid_via.hfb
```

For the overall flow and the commands for each starting state, see [quickstart.md](quickstart.md).

- Check that the conversion prints `stored_crc=0x.... match=True`.
- **Close the VIA page (browser tab) while flashing.** If VIA is communicating with the keyboard, it may interfere with the start of the flashing process.
- For how to choose the flash target and what to do when flashing stops partway, see [flashing.md](flashing.md).

The first time you flash `via` (or when you flash a version that changes the EEPROM layout), the keymap and settings start from the initial state. After that, the settings remain even if you flash a version with the same layout again.

## 2. Load the definition into VIA

This keyboard is not on VIA's official list, so you load the definition JSON yourself. The definition is `via/hhkb_hybrid.json` in the repository.

1. Open https://usevia.app in Chrome / Edge
2. Turn **Show Design tab** ON under the gear (Settings) at the top right
3. On the **Design** tab, press **Load Draft Definition** and choose `via/hhkb_hybrid.json`
4. On the **Configure** tab, press **Authorize device**, choose `HHKB Hybrid QMK` and connect

The loaded definition is saved in that browser, so from the next time on you can connect with step 4 alone. Load it again when you use another browser or PC, when you have cleared the site data, or when the definition JSON has been updated (custom keycodes or menus added, and so on).

The definition JSON is generated by `tools/gen_via_json.py` from `keyboards/hhkb_hybrid/keyboard.json` (the Japanese labels are output as `\uXXXX` because VIA does not interpret UTF-8).

## 3. Keymap

- There are 8 layers (0: Base, 1: Fn, 2–7: free). In the initial state, layers 0 / 1 have the same layout as the `default` keymap.
- **Put Fn on layer 1.** The stock-compatible Bluetooth key operations (Fn+Ctrl+1–4 and so on) are decided by "whether layer 1 is active" (this does not matter if you turn OFF "Bluetooth キー操作" (Bluetooth key operations) below).
- VIA macros can also be used. However, macro strings do not go through the JIS/US correction ([jis-us-toggle.md](jis-us-toggle.md)).

### Custom keys (Custom tab)

The **Custom** tab of VIA shows keys specific to this keyboard. You can assign them to any position and layer you like.

| Label | Name | Behavior |
|---|---|---|
| JIS | `JIS_TOG` | JIS/US correction ON/OFF |
| BT1–BT4 | `BT_SLOT1`–`BT_SLOT4` | Switch to Bluetooth slot 1–4. In pairing mode, pair in that slot |
| Pair | `BT_PAIR` | Enter pairing mode (equivalent to Fn+Q) |
| PCan | `BT_CANCEL` | Cancel pairing mode (equivalent to Fn+X) |
| USB | `OUT_AUTO` | Return the output to automatic (USB while connected over USB) (equivalent to Fn+Ctrl+0) |
| BDel1–BDel4 | `BT_DEL1`–`BT_DEL4` | When pressed in pairing mode, delete the registration of that slot (equivalent to Fn+Ctrl+Del+number after Fn+Q) |

The values of the custom keys (in order from `QK_KB_0`) are saved in the EEPROM together with the keymap, so on the firmware side they are never reordered and new ones are only appended at the end.

When built with `HHKB_JIS_US_TOGGLE=no`, `JIS_TOG` becomes a key that does nothing.

## 4. HHKB menu (keyboard-specific settings)

An **HHKB** menu is added to the VIA settings screen, and the following items are listed on the left.

| Item | Setting | Default |
|---|---|---|
| JIS/US 補正 (JIS/US correction) | JIS/US correction ON/OFF | Current state |
| JIS/US 補正 (JIS/US correction) | Whether Ctrl+Alt+Shift+J switches the correction | Enabled |
| 自動スリープ (Auto-sleep) | Time without operation until auto-sleep (1 / 5 / 10 / 30 / 60 minutes). On battery power only. Always disabled if DIP SW6 is ON | 30 minutes |
| Bluetooth キー操作 (Bluetooth key operations) | Whether to use the stock-compatible key operations (Fn+Ctrl+1–4 / Fn+Ctrl+0 / Fn+Q / Fn+X / Fn+Ctrl+Del+number). When OFF, you operate Bluetooth only with the BT keys of the Custom tab | Enabled |
| 設定の初期化 (Reset settings) | A button. See "Resetting the settings to the initial state" below | — |

- Settings are saved at the moment you change them.
- **VIA only reads the menu values when it connects.** If you switch the JIS/US correction with a key operation (`JIS_TOG` or Ctrl+Alt+Shift+J), the VIA display reflects it **when you reload the page**.

## 5. Resetting the settings to the initial state

Either of the following returns the keymap, macros and HHKB menu settings to the initial state. The JIS/US correction ON/OFF is kept.

- **The "設定の初期化" (Reset settings) button in the HHKB menu**: pressing it restarts the keyboard. Reload the page and connect again.
- **Connect USB while holding Esc (bootmagic)**: resets the settings and then enters the update mode for flashing (keys do nothing, so go on to flash firmware).

VIA's standard EEPROM reset exists only on the Debug screen of the development version, and moreover does not reset the keyboard-specific settings, which is why this button is provided.

## 6. When returning to the stock firmware

The VIA settings are saved in the EEPROM area `0x08080700–0x08080CFF`, which the stock firmware uses for its keymap (table B). If you return to the stock firmware with VIA data left in this area, the stock firmware loads it as a keymap, and **many keys cannot be input or produce characters different from their legends**.

Therefore, use one of the following when returning to the stock firmware. Both return the area to the stock state (zeros) before entering the update mode.

- **Flash the stock HFB with `tools/flash.py` (recommended)**: it detects automatically that the file is the stock HFB, sends the running QMK a command to erase this area, and then flashes.
- **Connect USB while holding Esc (bootmagic)** and then flash the stock HFB.

**Avoid entering the update mode with QMK's `QK_BOOT` key (Reset / Boot) to return to the stock firmware.** That path is also used for updating QMK, so it does not erase this area.

For the detailed steps, and for how to fix it when key input is already broken, see [restore-stock.md](restore-stock.md).

## Limitations

- Settings can be made only over USB. The changed keymap works as is with Bluetooth output too.
- Mouse keys, NKRO and system control (power/sleep) cannot be sent over Bluetooth. Media keys are limited to those the stock BLE firmware supports. Even if you assign these keys in VIA, they do nothing over Bluetooth (in this build mouse keys themselves are disabled).
- VIA macros are not subject to the JIS/US correction.
- When you flash a version that changes the EEPROM layout, such as the number of layers, the settings return to the initial state once, at the first startup.

## EEPROM usage (reference)

| Address | Use |
|---|---|
| `0x08080700–0x08080CFF` (1,536 B) | VIA storage area (QMK's eeconfig, VIA settings, the keymap for 8 layers, macros, 2 B of HHKB menu settings). The same area as keymap table B of the stock firmware |
| `0x08080300` | Valid mark of the stock keymap. The VIA build invalidates it when it initializes the area |
| `0x08080520` | JIS/US correction ON/OFF (the least significant bit of the stock sleep time setting byte, shared with the default build) |

QMK's standard EEPROM driver for the STM32L0 uses the EEPROM from its start, `0x08080000`, so it would corrupt the bootloader's boot check (`0x08080360` / `0x08080370`). For that reason the `via` keymap uses a dedicated driver (`keyboards/hhkb_hybrid/eeprom_hhkb.c`) that reads and writes only the area above. You can check with the following command that the built firmware does not reference any other EEPROM address.

```sh
python3 tools/check_eeprom_refs.py qmk_firmware/.build/hhkb_hybrid_via.bin
```

An analysis of where in the EEPROM the stock firmware and the bootloader write is in [reverse-engineering/stm32-analysis.md](reverse-engineering/stm32-analysis.md).

## Checking the running firmware (no writes)

Without writing to the keyboard, you can read out over Raw HID whether the VIA-enabled build is running and what the settings are. The target is QMK's Raw HID interface (`input1`, the hidraw whose report descriptor starts with `06 60 ff`; the one that `python3 tools/flash.py --list` shows as `FLASH TARGET`).

```sh
python3 - /dev/hidrawN <<'EOF'
import os, select, sys
fd = os.open(sys.argv[1], os.O_RDWR)
def cmd(p):
    os.write(fd, b"\x00" + bytes(p).ljust(32, b"\x00"))
    r, _, _ = select.select([fd], [], [], 1.0)
    return os.read(fd, 64)[:32] if r else None
rx = cmd([0x01])                                   # VIA protocol version
if not rx or rx[0] != 0x01:
    sys.exit("No response to VIA (QMK without VIA support, or not QMK)")
print("protocol 0x%04x" % ((rx[1] << 8) | rx[2]))    # 0x000d for the VIA-enabled build
print("layers", cmd([0x11])[1])                     # 8
rx = cmd([0x04, 0, 1, 0])                           # keycode of layer 0 / row 1 / col 0 (Esc)
print("L0 Esc = 0x%04x" % ((rx[4] << 8) | rx[5]))
# HHKB menu values ("HHKB menu value IDs" below)
print("menu", [cmd([0x08, 0x00, i])[3] for i in (1, 2, 3, 4)])
os.close(fd)
EOF
```

- These are read-only commands (`0x01` / `0x11` / `0x04` / `0x08`), so the EEPROM does not change.
- For matrix positions (row, col), see `matrix` in `keyboards/hhkb_hybrid/keyboard.json`.

## Notes for maintainers and developers

### Design decisions

- **VIA is adopted, and Vial is not used**: the QMK for Vial (vial-qmk) is based on an older point in time than upstream QMK, and replacing the QMK pinned in this repository with it would break the premise of reproducible builds. Also, with the official QMK build image as of September 2026 (Python 3.14), the vial-qmk build tools did not work as they are. Advanced features such as tap dance can be implemented in code, so VIA was judged sufficient for changing the layout in a GUI.
- **The JIS/US correction is converted in the firmware, not with layers**: trying to produce the symbols for a JIS environment with VIA layers alone would require making the physical Shift a layer-switching key, which breaks Shift+click, IME operations that use Shift pressed alone, and so on. Converting in the firmware lets Shift remain a real modifier key.
- **The stock Keymap Tool is not supported**: the Keymap Tool does not work on QMK. If you return to the stock firmware and write a keymap with the Keymap Tool, table B (the VIA storage area) is also rewritten, so when you flash the VIA-enabled build afterwards the settings start from the initial state.

### Order and capacity of the EEPROM area

The VIA storage area (1,536 B) is used in the following order from its start.

| Contents | Size |
|---|---|
| QMK's eeconfig | 37 B |
| VIA magic / layout options | 3 B / 1 B |
| Keyboard settings (HHKB menu) | 2 B |
| Keymap (120 B × 8 layers) | 960 B |
| Macros (the rest) | 533 B |

- One layer is 4 rows × 15 columns × 2 B = 120 B. Macros need at least 100 B because of a static check in QMK, so the maximum number of layers in this area is 11.
- The number of layers is `DYNAMIC_KEYMAP_LAYER_COUNT` in `keymaps/via/config.h`, and the area size is `EEPROM_SIZE` in the same file (`eeprom_hhkb.c` statically checks the upper limit of 1,536 B).

### The 2 B of keyboard settings and the layout version number

The 2 bytes of `VIA_EEPROM_CUSTOM_CONFIG_SIZE 2` are used in `hhkb_hybrid.c` as follows. **All defaults are 0**, so a freshly erased EEPROM reads as the defaults as is.

| Position | Contents |
|---|---|
| Upper 4 bits of byte 0 | EEPROM layout version number `HHKB_VIA_LAYOUT_VERSION` (1 or greater. Currently 2) |
| bit0 of byte 0 | **Disable** switching the JIS/US correction with Ctrl+Alt+Shift+J |
| bit1 of byte 0 | **Disable** the stock-compatible Bluetooth key operations |
| Byte 1 | Auto-sleep code (0 = 30 minutes, 1 = 1 minute, 2 = 5 minutes, 3 = 10 minutes, 4 = 60 minutes. Out of range means 30 minutes) |

- The VIA magic is made from the QMK build date and time, but `tools/build.sh` fixes the date and time with `SKIP_VERSION=1`. Therefore the VIA settings remain even if you flash a version with the same layout again.
- In exchange, when you make **a change that alters the EEPROM layout** (the number of layers, `VIA_EEPROM_CUSTOM_CONFIG_SIZE`, a change in the eeconfig size caused by updating QMK itself, and so on), increase `HHKB_VIA_LAYOUT_VERSION` in `hhkb_hybrid.c` by 1. If the version number does not match at startup (`via_init_kb()`), the keymap, macros and keyboard settings are initialized. If you forget to increase it, the old data is read at shifted positions.

### HHKB menu value IDs (VIA custom values, channel 0)

| ID | Item | Value exchanged with VIA |
|---|---|---|
| 1 | JIS/US correction ON/OFF | 0 / 1 |
| 2 | Whether Ctrl+Alt+Shift+J switches it | 0 / 1 |
| 3 | Auto-sleep | Number of minutes (1 / 5 / 10 / 30 / 60). The firmware converts to and from the code used for storage |
| 4 | Stock-compatible Bluetooth key operations | 0 / 1 |
| 5 | The "設定の初期化" (Reset settings) button | 1 when pressed |

- The handling is in `via_custom_value_command_kb()` in `hhkb_hybrid.c`, and the screen definition is `MENUS` in `tools/gen_via_json.py`. Keep the IDs and the order consistent in both.
- **Do not use the value 0 for a dropdown option.** usevia.app decides the value of an option with `value || idx`, so an option with the value 0 is sent replaced by its position number in the list (this was the cause of a bug where choosing "30 minutes" for auto-sleep resulted in 10 minutes).
- usevia.app does not interpret the loaded definition as UTF-8, so `gen_via_json.py` outputs Japanese as `\uXXXX`.
- usevia.app only reads the menu values when it connects. Even if a value changes on the keyboard side, the display is not updated until you reload the page.
- usevia.app's standard EEPROM reset exists only on the Debug screen of the development version, and moreover initializes only the keymap and macros. That is why the "設定の初期化" (Reset settings) button (ID 5) is provided.

### Notes on firmware internals

- **The EEPROM driver's format does not erase**: at startup QMK calls `via_init()` **before** the eeconfig initialization. If `eeprom_driver_format(false)` (called at first startup, by bootmagic and by resetting the settings) erased the area, the keymap and version number that VIA wrote just before would be lost, so `eeprom_hhkb.c` only invalidates the magic here. The bytes that were left return to the defaults through the eeconfig re-initialization, the VIA magic mismatch and the version number check.
- **Erasing the whole area (zeroing) happens only on the paths for returning to the stock firmware**: `AA AA F0 00 00` over Raw HID and bootmagic call `eeprom_driver_erase()`. The specification is in [reverse-engineering/implementation.md](reverse-engineering/implementation.md).
- **Receiving Raw HID**: in the VIA-enabled build VIA owns `raw_hid_receive()`, so the stock update commands (`AA AA …`) are handled in `via_command_kb()` before VIA.
- **USB is disconnected before moving to the update mode**: E0 / F0 / QK_BOOT / bootmagic disconnect USB and wait 500 ms before resetting (to make sure the host recognizes the disconnection).
- **VIA macros do not go through the JIS/US correction**: this is because QMK's macro sending (the `send_char` family) does not go through key processing (`process_record_kb`).
