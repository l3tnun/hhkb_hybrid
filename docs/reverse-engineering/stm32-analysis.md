# STM32 側逆向き解析メモ

HFB `HHKB800_FW_A048.hfb` (sha256=635b995e...) の STM32 アプリ部分 (`[4:4+0x10000]`, flash `0x08010000` 起点) と、
実機フルダンプ `hhkb_stock_128k.bin` のブートローダー領域を静的解析した記録。確定度合いは各項目に明記する。

- 作成: 2026-09-12
- 改訂: 2026-09-13 (MCU を STM32L072 に訂正。F103 前提の記述を訂正・削除。EEPROM/キャリブレーションを追記)

## 1. MCU: STM32L072RBT6 [確定]

- 根拠: ① チップシルク `STM32L072RBT6` ② L0 の GPIO (IOP バス) リテラル ③ L0 の NVM キー ④ EEPROM (`0x0808xxxx`) 参照

| リテラル | L0 での意味 | 旧解釈 (F1 前提, 誤り) |
|---|---|---|
| `0x50000400` / `0x50000800` / `0x50000C00` / `0x50001C00` | GPIOB / GPIOC / GPIOD / GPIOH | (未検出扱い) |
| `0x40010800` | **TIM21** | GPIOA |
| `0x40011400` | **TIM22** | GPIOD |
| `0x40010000` | SYSCFG | AFIO |
| `0x40010400` | EXTI | — |
| `0x40007000` | PWR | PWR |
| `0x40012400` | ADC1 | ADC1 |
| `0x40013000` | SPI1 | SPI1 |
| `0x40000400` | TIM3 | TIM3 |
| `0x40021000` | RCC | RCC |
| `0x40022000` | FLASH (NVM) | — |
| `0x89ABCDEF` / `0x02030405` | EEPROM (PEKEYR) キー | — |

- 既存パッチ (`-mcpu=cortex-m0` でアセンブル) は Cortex-M0+ 向けとして正しい
- 動作クロック (電池 4 MHz / USB 16 MHz)、TIM21 の 1 ms 刻み、キー走査の周期と 1 キーごとの手順 (OpAmp・C14・ADC の扱い) は [power-management.md](power-management.md) §7

## 2. SPI1 通信 [確定度高: バス。内容: 要実測]

- SPI1 (`0x40013000`) のみ使用。nRF (EYSHCNZWZ) との通信に使う。**STM32 はスレーブ** (2026-09-13 確認。詳細は `bluetooth-protocol.md`)
- レジスタ配置は L0 でも同じ (SR=+0x08, DR=+0x0C, CR2 bit6 = RXNEIE)
- 送信関数:
  ```asm
  push {r4,r5,lr}; cpsid i
  loop: ldr r4, [SPI1+8]          ; SPI1->SR
        ands r4, #2; beq loop     ; TXE 待ち (ポーリング)
        ldrb r4, [src, r0]
        str r4, [SPI1+0xC]        ; SPI1->DR
  cpsie i; pop
  ```
  → ブロッキングポーリング 8bit 送信。割込み/DMA なし
- 初期化の `SPI1->CR2 |= 0x40` は **RXNEIE** (受信割込み有効)。旧記載の「SSOE」は誤り
- ピン (確定): PA15=NSS, PB3=SCK, PB4=MISO, PB5=MOSI (AF0、MspInit)。要求線 PB6

### 2-1. nRF 送信経路 [確定度高]

| 項目 | アドレス/値 | 意味 |
|---|---|---|
| 送信バッファ | RAM `0x200016ba` (0x80B) | `0x8015a80` がゼロクリア |
| 送信フラグ / 長さ | `0x200000ca` / `0x200000cb` | フラグ=1 かつ長さ設定で送信開始 |
| 送信実行 | `0x8011146`: `bl 0x8015a98` | r0=buf, r1=len。スレーブなので nRF のクロックに合わせて 1 バイトずつ DR に載せる |
| フレーム形式 | `[0]=0x00, [1]=0xAA, [2]=cmd, [3..]=data` | |
| キーボードレポート | 応答種別 `0x01` (0x8010d02-0x8010d28) | nRF の cmd 02 への応答。`00 AA 01 mod k1..k6 00` (11 バイト) |
| キー release 系 | `cmd=0x02` (0x8010d4e) | `[3]` にレポートの一部 |
| その他 | `0xE5`(0x8010cb0), `0x40`(0x8010dd6), `0x08`(0x8010dfe), `0xE2`/`0xE3` | 意味は未確定 |
| コマンド系 4 バイトフレーム | `[0]=0x00/0x04, [1]=0xAA, [2]=0x80/0x40/0x10/0x64, [3]=0x00` | 0x801045a, 0x80105f8, 0x8010516, 0x80104ae 等。意味は未確定 |

純正 FW は USB と BT で同じ HID レポートを共有し、SPI で nRF へ転送している。
L0 版は SPI1 スレーブとして実装している (`keyboards/hhkb_hybrid/nrf_spi.c`)。

純正が持つ release 専用のコマンド (`cmd=0x02`) は、スロット切替の前に旧ホストへキー解放を送る処理の根拠でもある (既知の不具合と対策は [bluetooth-protocol.md](bluetooth-protocol.md) §11)。

## 3. HID レポート処理 [確定度高]

- `..`: HID レポート (modifier + 6KRO) へのキー追加処理
  - `0x8015b8e` = press 経路 (JIS/US トグルパッチの press report hook)
  - `0x8015b04` = release 経路 (release report hook)

## 4. EEPROM とキャリブレーション [確定]

| 処理 | 場所 | 内容 |
|---|---|---|
| キャリブレーション読み込み | | `0x08081100` から u16 ×128 を RAM `0x2000076A` へ |
| テーブル書き込み | | `0x08081000` ← RAM `0x2000066A`、`0x08081100` ← RAM `0x2000076A`、`0x08081310` ← 0xAAAA |
| 押下判定の閾値 | | 非押下時 `thr = cal[i] + ofs[i]` (cal=RAM `0x2000076A`, ofs=RAM `0x2000086A`)、押下中は `thr − 0x32`。フラグ `0x20000071` 時は固定 `0x55F` (押下中 `0x55F − 0xC8`) |
| 判定 | | `ADC 値 > thr` で押下 |
| ADC 読み取り | | ADSTP 待ち → ADSTART → EOC 待ち (各 10ms タイムアウト) → DR |
| ADC 設定 | | クロック同期 PCLK/1 (CKMODE=11)、12bit |
| EEPROM 書き込み HAL | | 32bit ワード書き込み、 でアンロック、 でロック |

- インデックス `i = col * 8 + row`
- QMK 実装: `ofs` を EEPROM `0x08081200` から読む Duncaen (Classic) 方式で実機のキー入力を確認済み
- 旧記録「キャリブレーションはブートローダー領域にある」は誤り (EEPROM にある)

### 4-1. EEPROM 書き込み範囲の全体像 [確定: 逆アセンブル]

純正アプリ (A048) とブートローダーで EEPROM を書き込む箇所を洗い出した結果 (2026-09-14)。
書き込み関数はアプリ `0x08012144`、ブートローダー `0x08002748` (いずれも 32bit ワード書き込み)。

| 範囲 | 中身 | 書き込み元 |
|---|---|---|
| `0x08080000–0x080802FF` | キーマップ表 A (モード n=0..2、`0x08080000 + n*0x100` から 0x80 ×2) | アプリ `0x0801B45C` / ブートローダー `0x08001FA8` (消去は `0x08001C78`) |
| `0x08080300` | キーマップのマジック (`0xAAAA` で有効) | アプリ `0x0801B63C` / ブートローダー |
| `0x08080310–0x0808034F` / `0x08080350` | 設定表 64B / マジック | アプリ `0x0801B400` / ブートローダー `0x080021C0` |
| `0x08080360` / `0x08080370` | 起動フラグ / アプリ CRC | E0・E3 (`hardware.md` 参照) |
| `0x08080380–0x0808047F` | BT 接続先の記録 16 件 × 16B (満杯で全消去 `0x0801AD98`) | アプリ `0x0801B148` |
| `0x08080500–0x08080513` | モード設定 5 ワード | アプリ `0x0801B288` / ブートローダー `0x08002234` |
| `0x08080520` | スリープ時間 (分) | アプリ `0x0801B620` |
| `0x08080700–0x08080CFF` | キーマップ表 B (n=0..2、`0x08080700 + n*0x200` から 0x80 ×4) | アプリ `0x0801B57C` のみ |
| `0x08081000–0x080812FF` | キー別の表 / キャリブレーション / オフセット表 (先頭バイトは起動判定) | アプリ `0x0801B360` `0x0801B500` / ブートローダー `0x0800BDA8` `0x0800BE8C` |
| `0x08081310` / `0x08081320` | テーブル有効マジック | 両方 |
| `0x08081330` / `0x08081338` | 版数 | ブートローダー `0x0800BF04` / アプリ `0x0801B674` |
| `0x08081350` / `0x08081360` | 更新要求 / 設定 | 両方 |
| `0x08081400–0x080816FF` | キーマップ表 A 後半 (`0x08081400 + n*0x100` から 0x80 ×2) | アプリ `0x0801B45C` のみ |

- HID 更新 (E0〜E3) で書き込むのは起動フラグ・CRC・更新要求のみ。キーマップ領域には触れない。
- 上記以外 (`0x08080480–0x080804FF`、`0x08080524–0x080806FF`、`0x08080D00–0x08080FFF`、`0x08081370–0x080813FF`、`0x08081700–0x080817FF`) は、定数参照としては見つからない。

### 4-2. キーマップの読み込みと既定値の書き戻し [確定: 逆アセンブル / 呼び出し時期は推定]

- `0x0801C744`: `0x0801B120` で `0x08080300 == 0xAAAA` を判定する。
  - 有効: 表 A (`0x0801B050`) と表 B (`0x0801B0CC`) を n=0..2 について読む。
  - 無効: 既定キーマップを RAM に読み込み (`0x0801D1EC`)、`0x0801B848` を呼ぶ。
- `0x0801B848`: `0x08080300 ← 0xFFFF` → 表 A と表 B を書き込み → `0x08080500` を更新 → `0x08080300 ← 0xAAAA`。
- `0x0801C744` の呼び出し元は `0x0801190C` / `0x0801A9D6` / `0x0801C0FA` の 3 か所 (起動時・モード判定時と推定。未実機確認)。
- 2026-09-13 の EEPROM ダンプ (DFU alt=2) では `0x08080300 = 0xAAAA`、`0x08080700–0x08080CFF` と `0x08081400–0x080816FF` は全ゼロ。
- ただし純正アプリより先に**ブートローダー**がマジックを確認する (`0x0800C498` → `0x080047A0`)。無効ならキーマップを既定値で RAM に読み込み、`0x08001FA8` で**表 A と `0x08080500` だけ**を書き直してマジックを `0xAAAA` に戻す。ブートローダーは表 B を参照しない。そのため、マジックを無効にしただけでは表 B の内容はそのまま純正アプリに読まれる [確定: 逆アセンブル + 実機]。
- QMK の VIA 対応は表 B の領域 (`0x08080700–0x08080CFF`) を VIA 用 EEPROM に使う。上記のため、純正に戻す前に表 B をゼロ (ダンプ時の純正状態) に戻す必要がある。表 B に VIA のデータを残したまま戻すと、純正でキー入力が崩れることを実機で確認した ([../via.md](../via.md), [../restore-stock.md](../restore-stock.md))。

## 5. Classic vs Hybrid の比較 [確定度高]

HHKB Professional Classic 純正 FW (`HHKB410_FW_A429.hfb`) と Hybrid 純正 FW のアプリ領域を比較した。

| 観察 | Hybrid | Classic | 意味 |
|---|---|---|---|
| 列マルチプレクサ定数 `0x70000000` / `0x60001000` / `0x00007000` (GPIOB BSRR 値) | ×16 / ×16 / ×16 | ×16 / ×16 / ×16 | 列選択回路は同一 |
| `0x40010800` (TIM21) | ×5 | ×4 | 両者とも L0 |
| `0x40011400` (TIM22) | ×1 | ×1 | 同一 |

- ユーザー観察 (基板写真): Classic と Hybrid の差は BT モジュールのみ
- Duncaen の行列実装 (行 B0/B1/B2/B10、列 B12-B14、C6/B15 選択、C7 OpAmp、C8 放電、ADC ch1) で実機のキー入力を確認済み

## 6. ブートローダー [確定]

起動判定・E0/E3・ジャンプ時の状態は `../hardware.md` を参照。

- リセット → (初期化) → → (起動判定)
- ブートローダーは HAL SysTick を使用 (`SysTick_Handler` =)、EXTI も使用 (`0x40010400` 参照あり)
- RCC_CSR (`RCC+0x50`) へのアクセスは静的スキャンで見つからない (リセット要因フラグを消さない)
- ブートローダー領域に純正アプリのバックアップは無い (一致率 5〜8% = 偶然の水準)

## 7. DFU 復旧の実機検証

- DFU (`0483:df11`) で純正アプリ部 64KiB を `0x08010000` に書き込み、フルダンプで確認
  - ブートローダー領域は書き込み前後で不変 (`d5722341...`)
  - アプリ領域は公式 HFB アプリ部と一致 (`f9fab50e...`)
- `0x08020000` 以降のアップロードは `LIBUSB_ERROR_IO`
- 注意: DFU 生書き込みは EEPROM の期待 CRC (`0x08080370`) を更新しない。書き戻したアプリの CRC16 と一致する場合だけ起動する (`../recovery.md` 参照)

## 8. 解析再現

```python
from pathlib import Path
data = Path('HHKB800_FW_A048.hfb').read_bytes()
app = data[4:4 + 0x10000]           # STM32 @ 0x08010000
boot = Path('hhkb_stock_128k.bin').read_bytes()[:0x10000]  # ブートローダー @ 0x08000000
```

逆アセンブル: capstone (`CS_MODE_THUMB | CS_MODE_MCLASS`)。PC 相対リテラルを解決して周辺レジスタ・EEPROM 参照を特定した。
