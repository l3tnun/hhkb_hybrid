# HFB 形式と HID 更新プロトコル

純正の更新ファイル `.hfb` の構造と、それを書き込む HID 更新プロトコル（E0/E1/E2/E3）の解析。実装は `tools/qmk_to_hfb.py`（変換）と `tools/flash.py`（書き込み）にある。書き込み手順の利用者向け説明は [../flashing.md](../flashing.md)、起動判定は [../hardware.md](../hardware.md) を参照。

## HFB コンテナ形式

```
[0:2]           ファイル CRC16-CCITT（HFB[2:] 全体に対する反射 CRC）
[2:4]           header64 = アプリ領域の CRC（ブートローダが起動判定に使う値）
[4 : 4+0x10000] STM32 アプリ領域 64 KiB（ロードアドレス 0x08010000）
[0x10004:]      nRF(Bluetooth) ファームイメージ + フッタ
```

- `tools/qmk_to_hfb.py` は純正 HFB をテンプレートに読み込み、**STM32 アプリ領域だけ**を QMK バイナリ（64 KiB 以内、末尾 `0xFF` 埋め）に差し替え、2 つの CRC を再計算する。
- `[0x10004:]`（nRF ファーム + フッタ）とコンテナ形式は純正のまま残す。QMK 化されるのは STM32 アプリ側だけで、Bluetooth 側は純正 nRF ファームをそのまま使う（[../../README.md](../../README.md) の「Bluetooth は純正 nRF ファームを流用しています」を参照）。

### 2 つの CRC

- **ファイル CRC**（`[0:2]`）: `HFB[2:]` 全体に対する反射 CRC16-CCITT。ファイル整合性チェック。
- **header64**（`[2:4]`）: アプリ領域の CRC。**ブートローダはこの値とアプリ実体の CRC16 が一致するときだけアプリへジャンプする**（詳細は [../hardware.md](../hardware.md)）。DFU での生書き込みはこの値を更新しないため起動しない。HID 更新（E0〜E3）はこの値まで更新するため、書き込み後そのまま起動する。

## HID 更新プロトコル（E0/E1/E2/E3）

各コマンドは `AA AA Ex …` で送り、正常応答は `55 55 Ex …` で返る。レポートサイズは更新モード（PFU ブートローダ）で 64 バイト、QMK の Raw HID 経由で E0 を送る場合は 32 バイト。

| コマンド | 送信 | 応答 | 役割 |
|---|---|---|---|
| **E0** | `AA AA E0` | `55 55 E0 00 00 00` | 更新モードへ遷移（EEPROM 起動フラグを落として再起動） |
| **E1** | `AA AA E1 00 08` + サイズ + CRC | `55 55 E1 00 00 00` | 転送開始（ファームサイズと HFB CRC を通知） |
| **E2** | `AA AA E2 00 <len+2>` + packet_no(LE16) + データ | `55 55 E2 00 00 02` + packet_no | データ転送。1 パケット最大 57 バイト |
| **E3** | `AA AA E3` | `55 55 E3 00 00 00` (+status) | 転送終了・確定 |

- **転送本体は `HFB[2:]`**（ファイル CRC の 2 バイトを除いた残り全体）。57 バイトずつ E2 で送る。
- E2 の応答には送信した packet_no がそのまま返るので、一致を確認してから次パケットへ進む。
- **E3 応答の status が 0 以外**の場合、転送が最後まで進んでいても FW が受理されていない可能性がある。そのため書き込み直前に HFB CRC を検証する（`flash.py` は不一致だと停止。`--allow-crc-mismatch` で明示的に上書き可能）。

## QMK 独自のコマンド（F0）

純正プロトコルには無い、このリポジトリの QMK（VIA 対応版）独自のコマンド。QMK の Raw HID（32 バイト）で受け付ける。

| コマンド | 送信 | 応答 | 役割 |
|---|---|---|---|
| **F0** | `AA AA F0 00 00` | `55 55 F0 00 00` | 純正キーマップ表 B（`0x08080700–0x08080CFF`、VIA の保存領域）をゼロに戻し、純正キーマップの有効マーク（`0x08080300`）を無効にしてから、E0 と同じ手順で更新モードへ遷移する |

- 純正 FW に戻す前に使う。表 B に VIA のデータが残ったまま純正に戻すと、純正 FW がそれをキーマップとして読み込み、キー入力が崩れる（[stm32-analysis.md](stm32-analysis.md) §4-2、[../restore-stock.md](../restore-stock.md)）。
- `tools/flash.py` は、書き込む HFB のアプリ領域に UTF-16 の "QMK" が含まれない（純正 HFB）かつ動作中が QMK のとき、E0 の代わりに F0 を送る。
- F0 を持たないファーム（VIA 非対応版や古い VIA 対応版）は、他の未知のコマンドと同じく `55 55 F0 01 00` を返す。`flash.py` はこのとき VIA のプロトコル版数の問い合わせ（`0x01`）に応答するかを調べ、VIA 対応版なら中止し（表 B を消せないため）、VIA 非対応版なら E0 で続行する（表 B を使っていないため）。

## 更新モード遷移と再列挙

- 動作中の QMK に E0（または F0）を送ると、QMK は応答を返してから USB を切断し（`usbDisconnectBus()` → `usbStop()` → 500 ms 待ち）、`hhkb_enter_update_mode()` が EEPROM を書いて再起動する。PFU ブートローダの更新モードで再列挙される。
- 純正 FW も E0 で遷移できる。純正の E0 処理（`0x0801ABE2`〜）は EEPROM を書いた後に空ループで待ってから `NVIC_SystemReset` するだけで、USB の切断は行わない。
- E0 後は USB デバイスが再列挙され `/dev/hidraw*` 番号が変わる。`flash.py` は更新モードの該当インターフェース（`input2` 相当）を自動で選び直す。番号変更で処理が止まった場合は、新しいデバイスを指定して `--resume`（E0 を飛ばして E1 から続行）で再開する。
- 書き込み先は更新モードのベンダー定義 raw HID インターフェース。判別方法は [../flashing.md](../flashing.md) を参照。

### 更新モードの再列挙で起きる USB エラー（-71）

観察された事実（2026 年 9 月、Linux / xhci_hcd）：

- 更新モード（bcdDevice 0.01）で列挙されるときに、カーネルが `can't set config #1, error -71`、`usbhid ... can't add hid device: -71`、`can't read configurations, error -71` などを出すことがある。QMK（bcdDevice 0.20）の列挙では観察されていない。
- 断続的に発生する。E0 / F0 / bootmagic のどの経路でも起き、更新モードのまま USB を手で挿し直した場合も 1 回目の列挙で失敗することがある。
- 手で挿し直した場合は、デバイスがすぐに切断・再接続して 2 回目の列挙で回復することが多い。E0 などの経路では、失敗したまま hidraw が作られずに止まることがある。
- QMK 側で更新モードへ移る前に USB を切断する処理を入れた後も発生したため、根本原因はブートローダ側の列挙とホストの組み合わせにあると見ている（未特定）。USB ハブ経由かどうか、VIA のページを開いているかどうかとの明確な相関は確認できていない。
- 更新モードに入った時点で起動フラグが落ちているので、挿し直しても更新モードのまま。`flash.py` は hidraw が現れないとき USB の抜き差しを案内して待ち、現れたら E1 から続行する（[../flashing.md](../flashing.md)）。

## 書き込み前の検証

`tools/qmk_to_hfb.py` は変換時に `stored_crc` と再計算 CRC の一致（`match=True`）を表示する。これは変換直後の自己確認であり、ビルドの再現性の照合にはならない。「意図したバイナリを再現できているか」は、`.bin` の sha256（`build.sh` と `qmk_to_hfb.py` が表示）か、アプリ領域の CRC（`header64` の変換後の値）で照合する（[../build.md](../build.md)）。
