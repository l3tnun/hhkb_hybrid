## 2. 取引の形 (nRF から見て)

```
コマンド送信のみ (83 xx / 85 xx / 61 xx / 93 xx の 2 バイト、84 + 30 バイト):
    CS low → バイト列を送る → CS high            (応答は読まない)

問い合わせ (01..06, A0, F0):
    CS low → cmd を送る
    0x00 を送りながら最大 100 バイト、受信が 0xAA になるまで待つ
    0xAA の後、N バイト読む (0x00 を送る) → CS high
        N: 01→1, 02→8, 03→2, 04→30, 05→1, 06→1, A0/F0→1
    0xAA が来なければ再試行 (01 は即再送、他はタイマー後、最大 600 回)
```

STM32 の応答は `00 AA <payload>` の形で、チェックサム・長さは無い。nRF は 0xAA までを読み捨てる。

## 3. nRF → STM32 の問い合わせと STM32 の応答

| nRF cmd | STM32 の応答 (0xAA の後) | 意味 | 確度 |
|---|---|---|---|
| 01 | `E5` | 起動時の hello。STM32 はこれを受けるまで起動待ち | 確定 |
| 02 | `01 mod k1 k2 k3 k4 k5 k6` | キーボードレポート (状態 2/3 のとき)。変化なしは `01` + 0 | 確定 |
| 02 | `02 cc 00 ...` | コンシューマ (メディア) キー | 確定 (STM32)。nRF 側の扱いは推定 |

| 02 | `10 00` → nRF cmd 06 に `slot` | **接続先の切り替え**: スロットの登録有無を問い合わせ → nRF が `61 00`(あり、そのスロットへ再接続を開始) / `61 01`(なし、何もしない) | 確定 (2026-09-13 詳細解析) |
| 02 | `40 00` → nRF cmd 03 に `01 slot` | **スロット slot でペアリング開始** (公開アドバタイズ、スロットのアドレス更新。新しい登録が既存を置き換える) → `83 02` → 登録完了で `83 (slot<<4)\|3` | 確定 (旧記載「接続」は誤り) |

| 02 | `40 00` → nRF cmd 03 に `04 00` | nRF 情報ブロック (84 + 30 バイト、FW 版 "0.29" を含む) の送信を依頼 | 確定 |
| 02 | `08` / `20` | FW 更新開始 / 最後の 83 状態の再送依頼 (純正 STM32 では前者は使われない) | 推定 |
| A0 / F0 | E2/E3 フレーム | nRF FW 更新の中継 (純正でも到達しない) | 確定 |

|---|---|---|

## 5. STM32 側の動き

- キー変化: スキャン後 で、状態 (`0x20000044`) が 2/3 かつレポートが保留中なら PB6 パルス → nRF が cmd 02 → レポート送信
- STM32 が始める手順は、すべて PB6 パルス → cmd 02 待ち (20ms × 3 回、だめならリセット) で始まる。以後の応答待ちは各 100ms
- 起動: nRF の `01` を待つ → 情報ブロック取得 → (`40` → `03` に `10`)
- 状態変数 `0x20000044`: 0/0x3C/0x3D = USB 系、1 = ペアリング、2/3 = BT 接続 (3 = 接続済み)、4 = BT 選択/再接続待ち、8 = その他

## 10. ペアリング・接続先切り替え・削除の流れ (2026-09-13 詳細解析)

中間生成物: `build/b4/pairing/`。**[C]** = コードで確認、**[I]** = 推定。

| 操作 (純正) | STM32 → nRF | nRF の結果 |
|---|---|---|
| Fn+Q | `40`→03 に `10 00` (待機)、状態 1 | `83 01` |
| 状態 1 で Fn+Ctrl+n | `40`→03 に `01 n` (ペアリング開始) | `83 02` → 登録完了で `83 (n<<4)\|3`。旧登録は新しい相手が保存された後に削除 [C] |
| Fn+Ctrl+n (通常) | `10`→06 に `n` | `61 00` なら再接続開始 (最大 60 秒で `83 (n<<4)\|3`)、`61 01` なら何もしない [C] |
| 状態 1 で Fn+Ctrl+Del の後 Fn+Ctrl+Del+n | `40`→03 に `02 n` | `85 00` 成功 / `85 01` 失敗 [C] |
| 状態 1/2 で Fn+Z の後 Fn+Z+Del | `40`→03 に `02 99` (全削除) | `85 00` [C] |
| Fn+X (状態 1/2) | ペアリング取り消し → 再接続スキャン | [C] |

- スロットごとに BLE アドレスが異なる (名前 "HHKB-Hybrid_n") [C]。同じ機器を別スロットに登録すると、Peer Manager で既存の鍵を上書きして元のスロットの登録が壊れる可能性 [I]
- 純正は、全スロット未登録なら自動で `01 00` (スロット 1 でペアリング) を送る [C]。QMK では真似しない
- 純正は応答待ちのタイムアウトで MCU をリセットする。QMK も同じ考え方でリセットする（待ち時間は長め。§13）

**既存の登録を消す/壊す操作**: `02 n`・`02 99`、登録済みスロットでの `01 n`、同じ機器を別スロットに再登録。安全な操作: `10 00`、`10`/06 の問い合わせ (登録済みなら再接続が始まる)。

## 11. QMK の実装 (B-4d)

- Fn+Ctrl+1〜4: `10`/06 で切り替え (接続中のスロットなら何も送らない)
- Fn+Q: `10 00` で待機 → ペアリング待ち。続けて Fn+Ctrl+n で `01 n`。Fn+X または 60 秒で取り消し (直前のスロットへ `10`/06)
- 削除 (`02 n`) は API のみ、キー割り当てなし
- B-4c-1 の「Fn+Ctrl+1 で未接続なら `01 00`」は誤りだった。テスト時は常に `83 03` で接続中だったため送信していない (診断 controls=0)
- 再接続の打ち切りは純正に合わせる（自動ペアリングはしない）。未接続なら `10`/06 で、切断後は何も送らず（nRF が自分で再アドバタイズ）、最大 60 秒（青 LED）。失敗後は `10 00` で nRF 待機、LED 消灯。電池かつ SW6 OFF なら STOP、SW6 ON / USB なら起き続け、キーまたは電源短押しで再試行。利用者向けの仕様は [../usage.md](../usage.md)

### スロット切替時に旧ホストへキー解放が届かない（既知の不具合）

BT 接続中に `Fn+Ctrl+n` で別スロットへ切り替えると、切替前のホストに Ctrl の押下が残る（押しっぱなしになる）ことがある。原因は、切替時に旧リンクへ全キー解放レポートを送らないことにある。

- `Fn+Ctrl+1〜4` は Ctrl 押下を検出条件にしたコンボで、切替の時点で Ctrl は物理的に押されたまま。Ctrl の押下レポートは切替前のホストへ送出済みだが、Ctrl の解放は切替後のリンクにしか届かない。
- QMK 側の `set_output_bt()`（`keyboards/hhkb_hybrid/hhkb_hybrid.c`）は出力パスが変わるときだけ `clear_keyboard()`（離れるパスの解放）を呼ぶ。BT→BT の切替は `output_bt` が変わらないため解放が送られず、`select_bt_slot()` はそのまま `nrf_spi_select_slot()` を送る。
- `nrf_spi.c` の `answer_poll()` は `control_pending` を最優先するため、解放レポートが nRF に読まれる前に切替要求（`10`/06、`40`→`03`）をキューすると解放は後回しになり、切替後のリンクへ送られる。解放→切替の順序を待ち合わせで保証する必要がある。
- 純正は `Fn+Ctrl+1〜4` で「キー送出を停止 → スロット選択」を行い、解放を `cmd=0x02` の release 経路で送ってから切り替える（§6、[stm32-analysis.md](stm32-analysis.md) §2-1）。QMK 実装にはこの解放ステップが無い。

対策（実装済み）：`hhkb_hybrid.c` の `bt_release_before_control()` が、切替系コマンド（`select`/`pair`/`idle`/`delete`）の送信前に `clear_keyboard()` で全キー解放レポートを nRF へ送出し、`nrf_spi_report_idle()` が真になる（nRF が読んだ）まで待ってから短く待つ（`jis_settle()` と同じ手法）。BT→USB の出力切替は `set_output_bt()` の BT 離脱時に同じ待ちを入れる。

## 13. 再接続できずに止まる不具合と、応答待ちのリセット (2026-10-07 静的解析)

### 症状（利用者の報告）

DIP SW6 ON・電池駆動の QMK で、ホストの Bluetooth を切るなどして切断させ、再接続の打ち切りで LED が消えたあと、しばらくしてからキーを押すと、青 LED が点いたまま再接続しない。電源の OFF→ON ではすぐに再接続する。発生までの時間は不明で、再現環境はない。

### 純正 STM32 の動き [C]

- **nRF への要求はすべて応答待ちで保護される**。要求の関数は最初に `0x080109fc` を呼ぶ: PB6 パルス → 20 ms 以内に cmd 02 が来なければパルスし直し、3 回失敗で `NVIC_SystemReset`（AIRCR = 0x05FA0004）。続く 06/03 の問い合わせ待ち（`0x0801cfb4`、各 100 ms）もタイムアウトでリセットする。リセット後はブートローダーが PD2 を High にするので、nRF もリセットされる（電源の入れ直しと同じ）。
- **状態 3 で切断**（`83 01`）: STM32 は何も送らず 60 秒待つ（`0x08019964`〜）。その後 `0x0801ad50`（`40`→03 に `10 00`、`83 01` まで 200 ms 間隔で最大 6 回）を送り、状態 5 へ。
- **状態 5 でキー**: 状態 4（`0x200000bb` = 1）→ 登録済みのスロット（`0x200000af[n]`）に `10`/06（`0x080104fc`）。`61 01`（未登録）なら自動ペアリング（`0x08010798`）、`61 00` なら最大 60 秒待って状態 5 か 0。

### 純正 nRF の動き [C]

- SPI の問い合わせ（`0x00028b24`）: 0xAA が 100 バイト来なければ、10 ms 後（app_timer 0x148 tick）に再試行、最大 600 回で諦める。再試行回数は成功で 0 に戻る。
- 通知・問い合わせのフラグ（`0x20002938`）は SPI 取引中（`0x2000293e`）でなければ 1 周に 1 件処理。メインイベント（`0x20002910`: キー送信、選択、待機、ペアリング、削除）は、nRF FW 更新中（`0x20003084`）や登録削除中（`0x20002b35`）なら処理されない。
- cmd 06（`0x00028950`）: 登録済みなら `61 00` を通知し、選択イベント → `0x0002a010`: 未接続なら `0x00029c5c`（モード 2、`0x00029484` で ble_advertising_init からやり直して FAST アドバタイズ、ホワイトリスト付き）。
- 02 の応答 `80 x`（電池）は、その場で Battery Service を更新する（`0x0002a770`）。05 の問い合わせが続くとは限らない。`10`/`40` には必ず 06/03 が続く（`0x00028c94`）。
- 切断時は SDK の ble_advertising が自動で再アドバタイズする（on-disconnect 有効。nRF 自身が切るときだけ `0x00029518` で無効にする）。
- System OFF（SVC 0x33）は使っていない。エラーハンドラ（`0x0002861c`）は何もしない（`bx lr`）ので、SoftDevice のエラーは黙って無視される。

### QMK との差と対策（実装済み）

nRF がどの状態で止まるかは静的解析では確定できない。純正は nRF が応答しないとリセットで立て直すが、QMK にはそれが無く、PB6 を 5 回打つと諦め、要求が残ったままになっていた（残った待機要求がスロット選択も止めていた）。対策は次のとおり（`nrf_spi.c`、`hhkb_hybrid.c`）。

| 対策 | 内容 |
|---|---|
| 応答待ち | hello の後、キー・メディアキー・電池（02 で読まれるまで）・接続先の要求（06/03 まで）が 1 秒以上読まれなければ「無応答」。純正の 20〜100 ms より長いのは SoftDevice のフラッシュ操作で nRF が止まる分の余裕。PB6 は最初 30 ms ごとに 5 回、その後は 100 ms ごとに打ち続ける |
| リセット | 無応答なら `mcu_reset()`（純正と同じ。電源 ON の経路と同じなので nRF もリセットされる）。Bluetooth 出力中だけ |
| やり直しのリセット（QMK 独自） | 打ち切り後（GIVEUP、nRF が未接続を報告済み）にキー・電源短押しがあれば、`10`/06 を送らずすぐリセット。実機（iPad の Bluetooth を 11 分 OFF → ON）で、`10`/06 では SPI は応答したまま再接続せず、リセット後は再接続したため |
| 待機要求の置き換え | まだ読まれていない待機要求（`10 00`）は、スロット選択で置き換える |
| 切断直後 | 純正と同じく 60 秒は何も送らない（nRF の自動再アドバタイズに任せる） |
| nRF の再起動 | 2 回目の hello で接続状態を消し、最後のスロットを選び直す |

### 制御要求の上書き（2026-10-07 修正）

QMK は、nRF が読んでいる途中の制御要求（02 に `10`/`40` で答え、06/03 がまだ来ていない）を新しい要求で上書きしていた。上書きすると nRF の 06/03 に答えられず、nRF はその問い合わせを 10 ms ごとに再試行する（再試行回数は他の取引が成功するたびに 0 に戻るので、止まらないことがある）。`control_start()` は、読み取り中の要求があれば最大 100 ms 待ってから次の要求を出す。

## 14. 電源 OFF で切断されない (2026-10-07 静的解析)

### 症状

電源ボタンの 2 秒長押しで OFF にしても、iPad 側で接続済みのまま残る。QMK が待機要求（`40`→03 に `10 00`）を確実に届けるよう直した後も変わらなかった。

### 原因（純正 nRF の不具合）[C]

- 待機要求の処理（`0x00029fbc`）は、接続中なら `0x000294fc` で切断する。ただし `0x20002a76`（通知の送信中）が 1 の間は切断を保留し（`0x20002a73` = 1）、`BLE_GATTS_EVT_HVN_TX_COMPLETE`（0x57、`0x00029da4`）で `0x20002a76` が 0 になったときに実行する。
- `0x20002a76` は送信中の通知数 `0x20003048` が 0 のときだけ 0 に戻る。通知を送るたびに +1（キー `0x0002a638`、メディアキー `0x0002a6c4` は 1 回に 4 通知、電池 `0x0002a770`）、HVN_TX_COMPLETE 1 回につき −1（`0x0002a8b0`）。SoftDevice はこのイベントの `count` で複数通知の完了をまとめて知らせるが、nRF は `count` を見ない。
- そのため通知数が実際より多いまま残り、接続中はゼロに戻らない（接続時 `0x0002a800` と切断時 `0x0002a850` でだけ 0 にする）。待機要求の切断は実行されない。純正 STM32 も `83 01` を 3 秒待つだけなので、同じ状況では純正でも切断されないはず。
- 同じ保留は、接続中に別スロットへ切り替えるとき（`0x0002a010` → `0x0002954c`）にもかかるはず（切り替わらないおそれ。実機では未確認で、QMK 側の対策もしていない）。

### 対策（QMK）

電源 OFF（`power.c` の `enter_off()`）では、待機要求を送って `83 01` を最大 3 秒待ったあと、PD2 を High にして nRF を止めてから STOP に入る。リンクはホスト側のタイムアウトで切れる。電源 ON はリセットで、ブートローダーが nRF を起動し直すので、止めたままで問題ない。
